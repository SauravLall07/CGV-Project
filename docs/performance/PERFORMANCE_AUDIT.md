# Chrono Express performance audit

Audit date: 15 October 2026 (Africa/Johannesburg). Scope: the repository's 122 JavaScript source modules, asset inventory, dependency graph, build configuration, scripts, and both test directories. This is an initial audit; no application code or assets were changed. Existing documentation and `dist/` were preserved.

Companion reports: [measurements and reproduction](PERFORMANCE_BASELINE.md), [implementation and regression plan](PERFORMANCE_OPTIMIZATION_PLAN.md).

## Executive summary

Chrono Express is a browser game written in JavaScript ES modules, using Three.js 0.185.1, Cannon ES 0.20.0, and Vite 8.2.2 as installed. It uses an imperative DOM HUD, not React. A single requestAnimationFrame loop updates persistent systems and the active level, renders a half-float post-processing pipeline, and draws a separate icon-only minimap. The level manager builds and disposes levels synchronously behind loading overlays.

The strongest evidence concerns startup size, synchronous construction, object counts, repeated UI work, and refresh-rate correctness. The in-memory production build contains 76,154,769 bytes across 53 files; its entry JavaScript is 1,511,152 bytes (443,703 bytes when locally gzip-compressed). The emitted FBX assets alone occupy 28,425,664 bytes. A Node scene census counted 3,069 meshes in Moving Heist and 2,018 in Timewreck, before visibility/frustum decisions. Initial construction in the mocked Node harness took 1,021.89 ms and 832.73 ms respectively. These construction measurements exclude real canvas painting, image decoding, character loading, shader compilation, and GPU uploads; they are not browser load-time estimates.

Several effective optimizations already exist: light pools with stable slot counts, conservative carriage visibility systems, nearby raycast sets with triangle grids, instanced vegetation, merged architectural geometry, zero-delta particle early exits, reduced-resolution bloom, a device pixel ratio cap, and adaptive render scale. Preserve these. A wholesale engine/framework rewrite is not justified.

No FPS, browser memory, GPU utilization, input-to-photon latency, or actual GC pause baseline could be recorded: the available computer/browser inventory returned no apps and no browsers. GPU-heavy rendering remains a profiling hypothesis, not a measured bottleneck. No Critical performance defect or browser memory leak is established. All 89 existing tests passed. One direct guard simulation established frame-dependent search rotation at 30/60/144 FPS.

Start with trustworthy instrumentation, production diagnostic gating, unchanged-value DOM guards, and minimap metadata caching. Next address the startup asset path and synchronous construction. Prioritize batching, GPU work, and deeper simulation changes using browser traces rather than predicted FPS gains.

## Evidence categories and priority

- **M — Measured:** build bytes, binary metadata, hash equality, scene census, Node timings, direct simulation results, test outcomes. Measurement environment and limits are in the baseline report.
- **C — Code-supported risk:** a cost or lifecycle path is directly present; its contribution to browser performance has not been measured.
- **H — Hypothesis:** likely cost requiring a browser trace or GPU experiment before implementation.

Severity expresses impact if encountered and the breadth of affected paths. It is not a claim of measured FPS loss. Complexity: S = localized; M = several interacting modules; L = asset pipeline or structural work. Regression risk assumes the proposed scoped implementation. No numeric improvement is promised without a measured comparison.

## Rendering review and visual constraints

Normal frame flow is update -> explicit canvas clear -> composer RenderPass -> bloom -> final output -> scissored icon minimap. There is no evidence that the full world is rendered twice for the minimap: `src/ui/minimap.js:58` uses a separate scene. Composer passes are intentional, not accidental repeated rAF chains. The outer clear plus RenderPass clear is a small candidate for verification, not a reason to remove safety clears without checking settings, resize and direct-render fallbacks.

Instancing/batching is appropriate for repeated static prop pieces and spatially partitioned vegetation. It is inappropriate to merge all carriages into one object: that defeats the existing zone/portal visibility, dynamic wreck transforms and interactive focus boundaries. Geometry sharing reduces memory even where draw count cannot change. An atlas can combine compatible tiny decorative maps only if UV repeat, normal-map color space, mip seams, transparency order and per-prop highlights remain identical. Start with geometry sharing; atlas work is lower-confidence.

Keep color grade, bloom footprint, grass density, foliage silhouettes, shadows, mist, lasers, time wave, ghost opacity and animation curves as reference appearance. Post-off/unlit/scenery-hidden/shadow-off toggles are diagnostic experiments only. Disabling them is not an accepted optimization. KTX2, different model encodings, static shadow caching and shader changes require image comparisons and hardware compatibility checks. Uncompressed model conversion can change nothing visually yet still lose if load/parse time or transfer grows; measure all three.

For fixed cameras and truly static paused/credits states, cached rendering may help. Do not apply global rendering-on-demand to a running game or the animated title. Do not freeze shadows with animated guards, doors, player or changing moon direction without invalidation.

## CPU, timing and input review

Highest measured blocking operation is level construction in the Node harness, not an established browser per-frame hot function. Trace `createBoardingLevel`, `createMovingHeistLevel`, `createTimewreckLevel`, texture noise/normal generation, FBX parse/smoothing, grass placement, PMREM/compile/upload and first nearby-grid construction during startup. During play, separately time timeSystem.update, level.update, stealth/LOS, player collision, camera raycast, interaction, HUD, culling hooks, renderer traversal and minimap.

Movement already uses delta and collision substeps. Time callbacks already split long frames at history sample boundaries. Cannon already uses `step(1/60, abs(scaledDelta), 3)` (`src/levels/timewreck.js:1894`) only for active debris; the small body count does not justify a new broad-phase engine. At severe stalls the frame cap discards elapsed wall time, and Cannon's max substeps may drop accumulated catch-up. Document these policies and test them before considering a unified fixed step. An accumulator rewrite can alter collision, puzzle windows, energy, strain, Throw release, respawn and cinematic timing; it belongs behind measurement and equivalence tests.

The confirmed ALERT search defect and cumulative exterior glitch bob must be separated from performance fixes. Preserve an explicitly selected intended reference rather than preserving different accidental behaviors at every FPS. First/third camera easing also uses some clamped linear delta blends; existing 30/60/144 tests provide useful regression protection, but not proof of identical trajectories under arbitrary stalls.

Keyboard repeat filtering, edge presses, blur clearing, pointer-lock loss pause and centralized input-state gating are good. Immediate actions run from key events; ordinary movement is polled once per render. The mixer ordering concern affects animation pose, not a demonstrated delay in player translation. Test mouse-to-camera response, UI focus/rebinding, fullscreen denial, missed keyup and actual click-to-visible response on hardware. No controller/touch parity is promised by the code.

## Memory and lifecycle review

`src/core/dispose.js:7` deduplicates geometry/material/texture releases across supplied roots, handles shader uniform textures, instanced buffers, skeleton bone textures and light shadow resources. Level disposers unregister gameplay callbacks and remove scene branches. Police clones detach before shared visual-resource cleanup and dispose owned skeleton textures (`src/entities/police-visual.js:484`). Storm debris explicitly disposes its detached group (`src/levels/timewreck-atmosphere.js:261`); grab handles free their owned geometries/materials (`:445`). These are not missing-disposal findings.

The Node lifecycle census left one scene child, the intended persistent player, after each tested L2/L3 teardown. It does not establish GPU or heap leak freedom. Persistent canonical textures/canvases, nature assets, police template, music/SFX buffers, PMREM generator, menus and input are intentional caches/owners. Their size and final shutdown need policy, not indiscriminate disposal between levels. Texture object counts alone miss CPU images, shared Sources, audio buffers and driver memory.

History arrays, rewind temporary arrays, minimap array/mesh churn and ray hit objects are stronger GC candidates than occasional event-time puzzle arrays or one projectile. Do not pool every object. Reuse only allocations shown to matter, with explicit ownership so a reused snapshot cannot mutate retained history.

Respawn timers have cancellation tokens/pause handling and tests; HUD/load screen timers and most UI/input listeners have disposal. Root-level singleton subscriptions and rAF persist for the page. There is no established level-restart event-listener leak. Verify with 20 restarts/quit cycles and browser heap retaining paths, then a 30-minute session.

## Assets, startup and dependency conclusions

All 52 source asset files were inventoried and SHA-256 checked; no entire-file duplicates were found. Embedded glTF image duplicates do exist (P13). Binary header parsing found nature surface maps are 1024x1024; embedded nature maps mostly 512x512, with tree cards 1024x512 or 1536x512. The eight surface JPGs alone represent approximately 42.67 MiB if resident as RGBA8 with full mip chains (a sizing model, not measured VRAM). Reducing JPEG transfer size alone does not reduce that storage. Normal maps must stay linear.

Required immediately: entry/core/UI, opening Boarding construction and appearance, player/visible guard rigs and their initial animations. Present implementation eagerly awaits all character clips, including later actions, plus nature surfaces/props. Candidates for later loading: non-opening actions with predictable prefetch before their first use, later levels/Cannon, unused police turn, future-level music. The title backdrop is playable Level 1 and gets adopted; do not rebuild it merely to implement lazy loading. Music and SFX start decoding after an audio-unlocking gesture and can overlap boot if the gesture occurs early.

Five source binaries are not emitted by the measured production graph: detective `Walking.fbx`, `Jumping.fbx`, `textures/cracked-stone.png`, `textures/train-tracks.jpg`, and `textures/backdrop/night-mountains.png`. Removing these would reduce repository size, not this production download. No deletion is proposed during this audit.

The only direct runtime dependencies are used; no duplicate installed Three/Cannon versions were observed. Development editor/overlay bodies are eliminated from production; tiny top-level residues remain (97/103 rendered pre-minification characters respectively), so shipping the full workshop is not a real finding. Recurring detective/music diagnostic strings do remain in production. DRACO loader is lazy; five decoder support files are emitted, but uncompressed GLBs declare no Draco extension. Emitted decoder bytes must not be reported as mandatory startup downloads: decoder fetching is on demand. Tree shaking works for unreachable helpers; split along actual level/loader boundaries instead of manually chunking arbitrary packages. No dependency upgrade is recommended solely for version age.

## Platform and outstanding profiling conclusions

The implemented controls target desktop keyboard/mouse browsers with WebGL2, Pointer Lock and Web Audio. Fullscreen/keyboard lock is optional through fallback handling. Actual Chrome/Edge/Firefox/Safari and mobile compatibility/performance were not tested. Mobile has neither a playable touch control scheme nor a measured thermal/memory baseline; do not claim mobile support based on the viewport tag. Test integrated GPUs, high-DPI and 144 Hz displays as well as capable GPUs. Keep capable devices at current quality and expose fixed tiers; do not silently add lower-detail rendering as a substitute for profiling.

Deployment headers, GPU timing-query support, disjoint/context-loss behavior, shader compilation on real GPUs, audio decoded memory, browser GC, prolonged sessions, restart VRAM trends, browser startup/asset load times and physical input latency remain open. The baseline report gives explicit reproducible collection steps; the plan gates high-risk work on them.
